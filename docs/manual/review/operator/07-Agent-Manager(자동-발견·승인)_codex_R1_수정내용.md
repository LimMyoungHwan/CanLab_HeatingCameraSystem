# 07-Agent-Manager(자동-발견·승인) — codex 검토 (Round 1)

## 종합 평가
- 수정 필요도: 중
- 한 줄 요약: 핵심 운영 흐름은 간결하지만, 설치 명령의 실행 위치·선행 조건과 설정 파일 위치, 승인 상태 용어 및 장애 복구 절차를 보완해야 실제 운영자가 안전하게 수행할 수 있다.

## 수정 필요 항목
1. [도입부] 문제: “PC당 1개 운영자 세션 콘솔 앱”이 어느 PC에서 실행되는지 모호하다. -> 제안: “각 Agent PC의 Windows 사용자 세션에서 하나씩 실행되는 콘솔 앱”처럼 설치 대상을 명시한다.
2. [도입부] 문제: “수동 Agent 기동(3.5)과는 택일”만으로는 두 방식을 동시에 사용했을 때의 영향이 설명되지 않는다. -> 제안: 동일 카메라에 대해 Agent 중복 실행 또는 충돌 가능성이 있으므로 Agent Manager 사용 시 수동 Agent를 실행하지 말라는 경고를 추가한다.
3. [7.1 설치] 문제: 명령을 어느 디렉터리에서 실행해야 하는지와 관리자 권한 필요 여부가 없다. `dotnet publish`와 `.\docs\deployment\...`는 저장소 루트 실행을 전제로 보인다. -> 제안: “저장소 루트에서 관리자 권한 PowerShell로 실행” 여부를 실제 스크립트 조건에 맞게 명시한다.
4. [7.1 설치] 문제: `--self-contained false`인데 대상 PC의 .NET 8 런타임 선행 설치 조건이 없다. 또한 게시 결과인 `publish\Manager`와 `-InstallRoot C:\HeatingCameraSystem`의 관계가 설명되지 않는다. -> 제안: 필요한 .NET 런타임 종류와 `install.ps1`이 게시 파일을 설치 경로로 복사하는지, 별도 복사가 필요한지를 명시한다.
5. [7.1 설치] 문제: 예약 작업 시작 후 정상 설치를 확인하는 절차가 없다. -> 제안: `Get-ScheduledTask -TaskName HCS-Manager` 등의 작업 상태 확인 방법과 Manager 콘솔 또는 로그에서 NATS 연결·카메라 검색 성공을 확인하는 기준을 추가한다.
6. [7.2 설정 파일] 문제: 두 JSON 파일의 실제 저장 위치와 생성 시점이 없다. 관리자가 파일을 찾거나 백업·복구할 수 없다. -> 제안: 각 파일의 절대 또는 `InstallRoot` 기준 상대 경로, 최초 생성 시점을 표에 추가한다.
7. [7.2 설정 파일] 문제: 필드 표기가 JSON 구조와 혼재되어 있다. `Cameras[](HardwareId/...)`는 읽기 어렵고 `Approved=False`, `IsApproved=true`처럼 동일 상태를 서로 다른 이름으로 표현한다. -> 제안: 실제 필드명인 `IsApproved`와 JSON 불리언 값 `true/false`로 통일하고 `Cameras[]`의 하위 필드를 별도 표기한다.
8. [7.2 설정 파일] 문제: `manager-state.json`은 직접 편집 금지라고 했지만 `manager-settings.json`의 안전한 편집 방법과 적용 시점이 없다. -> 제안: Manager 종료 후 편집해야 하는지, 변경 후 재시작이 필요한지, 잘못된 설정 시 복구 방법을 명시한다.
9. [7.3 카메라 승인 운영] 문제: “Agent 설정 화면”, “디바이스 관리 탭”, “대시보드”가 Master 화면인지 Agent Manager 화면인지 구분되지 않는다. -> 제안: 각 화면의 소속 프로그램과 정확한 메뉴 경로를 명시하고 문서 전체에서 동일한 화면 명칭을 사용한다.
10. [7.3 카메라 승인 운영] 문제: “대시보드에 초록 점”만으로는 어느 항목의 상태 표시인지 불명확하며, 프로세스 기동만으로 촬영 준비가 보장되는지도 알 수 없다. -> 제안: 해당 카메라/Agent 행의 연결 상태가 초록색인지 명시하고, 준비 완료 판단에 필요한 추가 상태가 있다면 함께 제시한다.
11. [버튼 표] 문제: “거부”가 단순 승인 취소인지 향후 자동 발견·재표시까지 막는 동작인지 설명되지 않는다. -> 제안: 거부 후 목록 상태, 재승인 가능 여부 및 USB 재연결 시 동작을 명시한다.
12. [버튼 표] 문제: “이름 저장”의 Alias가 상태 파일과 LiteDB에 중복 저장된다고만 되어 있어 변경 시 기존 레시피에 미치는 영향이 불명확하다. -> 제안: Alias 변경 후 `Recipe.CameraAlias`와 불일치하면 해당 레시피의 카메라 매칭이 실패할 수 있음을 경고하고, 관련 레시피 갱신 절차를 안내한다.
13. [버튼 표] 문제: “시리얼 설정”의 항목, 전송 성공 확인 방법, Agent 미연결 시 동작이 없다. -> 제안: 실제 화면 필드와 적용 시점, 성공·실패 표시를 간단히 설명한다.
14. [버튼 표] 문제: “로그 가져오기”에서 NDJSON과 gzip은 구현 형식이지만 운영자가 어디에서 기간·대상·저장 위치를 선택하고 결과를 확인하는지 알 수 없다. -> 제안: 사용자 동작과 결과 표시 위치를 중심으로 설명하고, 파일 형식은 참고 정보로 분리한다.
15. [[참고] 반복 크래시] 문제: “5회 초과”가 6번째 실패를 뜻하는지 모호하고 실패 횟수 초기화 조건도 없다. “영구 드롭” 역시 운영 문서 용어로 직관적이지 않다. -> 제안: 실제 판정 횟수와 카운터 초기화 조건을 명시하고 “자동 재시작 중지(`IsDisabled=true`)”로 표현한다.

## 누락/추가 제안
- USB 카메라가 자동 발견되지 않을 때 확인할 항목(WMI 인식, 장치 관리자 표시, Manager 재시작 또는 재검색 방법)을 추가한다.
- 동일 모델 카메라 여러 대를 연결할 때 `HardwareId`가 안정적으로 구분되는지와 USB 포트 변경 시 신규 장치로 등록될 가능성을 설명한다.
- 카메라 분리·교체 시 기존 등록 정보와 Alias를 정리하거나 새 하드웨어에 다시 승인하는 절차를 추가한다.
- NATS 연결 실패, Agent 실행 파일 누락, 승인 후 Agent 기동 실패를 구분할 수 있는 상태 또는 로그 확인 위치를 추가한다.
- 예약 작업의 로그온 조건, 자동 시작 확인 및 제거·재설치 절차를 간략히 안내한다.

## 이미지 자리 검토
- [그림 10] 적절 — 승인 절차 바로 뒤에 있어 배치가 유용하고 캡처 대상과 상태도 지정되어 있다. 다만 미승인 상태뿐 아니라 선택된 카메라의 `HardwareId`, Alias, 승인·거부 버튼, 시리얼 설정 및 상태 표시가 식별되도록 표시 영역을 구체화하고 민감한 PC·네트워크 정보는 마스킹하도록 안내하는 것이 좋다.
