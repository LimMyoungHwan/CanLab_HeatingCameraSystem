# 03-설치 — codex 검토 (Round 1)

## 종합 평가
- 수정 필요도: 높음
- 한줄 요약: 기본 설치 흐름은 갖추었으나 방화벽 방향, 카메라 인덱스 확인 방법, 실행 파일명과 다중 Agent 운용 조건을 바로잡고 실제 운영 환경을 기준으로 검증 절차를 보완해야 한다.

## 수정 필요 항목
1. [3.1 사전 요구사항] 문제: `.NET 8 (SDK/Runtime)`가 필수라고만 되어 있어 운영 PC에도 SDK가 필요한 것으로 오해할 수 있다. 또한 현재 `dotnet publish` 명령은 프레임워크 종속 배포이므로 런타임 설치가 필요하다는 설명이 없다. → 제안: 빌드 PC에는 .NET 8 SDK, 운영 Master PC에는 .NET 8 Desktop Runtime, Agent PC에는 .NET 8 Runtime이 필요하다고 구분한다. 자체 포함 배포를 사용할 경우 운영 PC의 런타임 설치가 불필요하다는 점도 명시한다.
2. [3.1 사전 요구사항] 문제: NATS 서버의 “Docker 권장”만 있고 Docker Desktop 또는 Docker Engine과 Compose 플러그인의 설치·기동 조건이 없다. → 제안: Docker 기반 절차를 사용할 경우 `docker version`과 `docker compose version`으로 사전 확인하도록 추가한다.
3. [3.2 방화벽] 문제: 4222/tcp의 인바운드 대상은 NATS 호스트이고, Master와 Agent는 NATS 서버로 아웃바운드 연결한다. 현재 표의 “대상 PC”와 방향 표현은 역할별 규칙을 명확히 구분하지 못한다. → 제안: NATS 호스트의 4222 인바운드, Master/Agent의 4222 아웃바운드, NATS 호스트의 8222 인바운드(선택), Master의 PLC 2004 아웃바운드로 나누어 작성한다.
4. [3.2 방화벽] 문제: 8222 모니터링 포트를 외부에 개방할 때의 보안 경고가 없다. → 제안: 운영망 전체 공개를 피하고 관리자 PC 또는 관리망에서만 접근하도록 제한하며, 사용하지 않으면 개방하지 않는다고 명시한다.
5. [3.2 방화벽] 문제: PLC의 2004/tcp만 기술되어 있고 Master PC에서 PLC IP까지의 네트워크 연결 조건이 없다. → 제안: Master와 PLC의 IP 주소·서브넷·게이트웨이를 확인하고 `Test-NetConnection -ComputerName <PLC_IP> -Port 2004`로 검사하도록 추가한다.
6. [3.3 NATS 서버] 문제: 명령을 어느 디렉터리에서 실행해야 하는지 명확하지 않다. `docs/deployment/docker-compose.yml`은 저장소 루트 기준 상대 경로이다. → 제안: “저장소 루트에서 PowerShell을 열고 실행”이라고 명시하거나 compose 파일의 절대 경로를 사용한다.
7. [3.3 NATS 서버] 문제: `127.0.0.1` 검사는 NATS 호스트 내부 연결만 확인한다. 원격 Master와 Agent에서 접근할 수 있는지는 검증하지 못한다. → 제안: 각 Master/Agent PC에서 `<NATS_SERVER_IP>:4222` 연결을 검사하고, `hardware.json`과 `agent.json`에도 동일한 주소를 입력하도록 안내한다.
8. [3.3 NATS 서버] 문제: 컨테이너가 실행 중이라는 사실만으로 NATS 서비스가 정상이라는 결론을 내릴 수 없다. → 제안: `docker compose ps`, `docker compose logs nats` 및 4222 포트 검사를 함께 수행하고 재시작 정책도 확인한다.
9. [3.4 Master 설치] 문제: `dotnet publish` 명령의 실행 위치가 명시되지 않았고 프로젝트 파일 경로도 생략되어 있다. → 제안: 저장소 루트에서 실행한다고 밝히고 `dotnet publish .\HeatingCameraSystem.Master\HeatingCameraSystem.Master.csproj -c Release -o .\publish\Master`처럼 명확한 경로를 사용한다.
10. [3.4 Master 설치] 문제: `hardware.json`을 수정한 뒤 적용 시점이 안내되지 않았다. → 제안: Master를 종료한 상태에서 PLC IP, NATS URL, PLC 디바이스 주소와 시리얼 포트를 수정하고 재시작해야 적용된다고 명시한다.
11. [3.4 Master 설치] 문제: PLC 디바이스 주소 중 일부가 현장 확인이 필요한 플레이스홀더라는 중요한 주의사항이 없다. → 제안: `ServoSpeedPercent`, `BitEmergencyStop`, Y축 JOG 비트, `ServoPointYBase` 등은 실제 PLC 명세와 대조한 후 사용해야 하며 확인 전 자동운전을 금지한다고 경고한다.
12. [3.4 Master 설치] 문제: 설정 파일을 처음 생성하기 위해 실행한 Master를 언제 종료하고 설정을 편집해야 하는지 흐름이 끊긴다. → 제안: “최초 실행 → 설정 파일 생성 확인 → Master 종료 → `hardware.json` 편집 → Master 재실행” 순서로 절차화한다.
13. [3.5 Agent 설치] 문제: 예시 실행 파일이 `Agent.exe`로 표기되어 있으나 publish 결과의 실제 실행 파일명과 일치하는지 불명확하다. 프로젝트명 기준으로는 `HeatingCameraSystem.Agent.exe`가 생성될 가능성이 높다. → 제안: publish 폴더에서 실제 파일명을 확인하여 모든 명령과 설명에 동일하게 사용한다.
14. [3.5 Agent 설치] 문제: 단일 인스턴스 절차에서 `agent.json`이 생성된 뒤 반드시 편집하고 재시작해야 한다는 설명이 부족하다. → 제안: 최초 실행 후 종료하고 `AgentId`, `NatsUrl`, `CameraIndex`, `StoragePath`, `SimulationMode`를 설정한 다음 재실행하도록 단계화한다.
15. [3.5 Agent 설치] 문제: 다중 인스턴스가 “안전하다”는 표현은 과도하다. 동일한 `AgentId`, `CameraIndex` 또는 `StoragePath`를 사용하면 메시지 대상과 캡처 파일이 충돌할 수 있다. → 제안: 인스턴스마다 고유한 `AgentId`, 올바른 `CameraIndex`, 별도의 `StoragePath`를 지정하고, `RecipeStep.CameraIndex`가 `Agent_{CameraIndex}`로 매핑된다는 규칙을 명시한다.
16. [3.5 Agent 설치] 문제: `SimulationMode`의 값 형식과 운영 환경에서의 권장값이 없다. → 제안: 허용되는 실제 값과 예시 명령을 제시하고, 실카메라 검증 시 시뮬레이션 모드를 비활성화해야 한다고 명시한다.
17. [3.6 카메라·시리얼 포트 확인] 문제: 장치 관리자에서 확인한 카메라 모델명만으로 OpenCV의 `CameraIndex` 0/1을 확정할 수 없다. 카메라 인덱스는 연결 순서와 드라이버 상태에 따라 달라질 수 있다. → 제안: Agent의 카메라 탐색 결과 또는 실제 미리보기·시험 캡처를 통해 인덱스를 하나씩 검증하고, USB 포트를 변경하거나 장치를 재연결한 뒤에는 다시 확인하도록 안내한다.
18. [3.6 카메라·시리얼 포트 확인] 문제: “USB 가상 시리얼”과 “시리얼 셔터”의 관계가 불분명하고 기본 통신 조건도 없다. → 제안: 장치 관리자에서 COM 번호를 확인한 뒤 `hardware.json`의 시리얼 설정에 반영하고, 기본값 `COM3`, `9600 8N1`은 실제 장비 설정과 다를 수 있음을 경고한다.
19. [3.6 카메라·시리얼 포트 확인] 문제: 셔터 통신을 일반 ASCII 명령으로 오해할 여지가 있다. → 제안: 셔터는 raw binary 프로토콜을 사용하므로 터미널 프로그램에서 문자열을 입력해 시험하지 말고, Master의 셔터 기능으로 열기·닫기를 검증하도록 명시한다.
20. [3.7 설치 검증 체크리스트] 문제: `dotnet --info 8.x`는 실제 출력 형식이나 판정 기준으로 사용할 수 없다. → 제안: Master PC는 `dotnet --list-runtimes`에서 `Microsoft.WindowsDesktop.App 8.x`, Agent PC는 `Microsoft.NETCore.App 8.x` 존재 여부를 확인하도록 변경한다.
21. [3.7 설치 검증 체크리스트] 문제: NATS 검증 주소가 항상 `127.0.0.1`로 고정되어 원격 설치 환경을 검증하지 못한다. → 제안: NATS 호스트에서는 `127.0.0.1`, Master와 Agent에서는 실제 NATS 서버 IP 또는 호스트명을 사용하도록 구분한다.
22. [3.7 설치 검증 체크리스트] 문제: `'Connected to NATS'`, `'Camera ready'`가 실제 프로그램에 출력되는 정확한 로그 문자열인지 확인 근거가 없고, 문자열 하나만으로 카메라와 메시징 전체를 검증하기 어렵다. → 제안: 실제 빌드에서 출력되는 로그 문구로 통일하고, 시험 캡처 명령 전송과 결과 수신까지 종단 간 검증 항목으로 추가한다.
23. [3.7 설치 검증 체크리스트] 문제: “Master 인식”의 녹색 점 위치와 의미가 구체적이지 않다. → 제안: 화면의 정확한 메뉴·패널명, Agent ID, 마지막 하트비트 시각 또는 온라인 표시를 함께 확인하도록 작성한다.
24. [3.7 설치 검증 체크리스트] 문제: PLC 확인 항목이 선택 사항처럼 보이지만 실제 PLC를 사용하는 운영 설치에서는 필수이며, 단순 값 갱신만으로 쓰기 동작의 안전성을 검증할 수 없다. → 제안: 시뮬레이션 설치와 실장비 설치를 구분하고, 실장비에서는 비상정지 상태와 주변 안전을 확인한 뒤 읽기 상태부터 검증하며 쓰기·구동 시험은 현장 승인 절차에 따라 수행하도록 한다.
25. [전체] 문제: 명령 실행 권한, 설치 폴더 권한, 로그·이미지 저장 공간, 재부팅 후 자동 시작 방법이 빠져 있다. → 제안: 관리자 권한이 필요한 단계, 서비스 계정 또는 시작 프로그램 등록 방식, `ImageStorage` 용량 점검과 정리 정책을 별도 절로 추가한다.

## 누락/추가 제안
- 설치 전 Master, Agent, NATS, PLC의 IP 주소와 호스트명을 기록하는 “현장 네트워크 정보표”를 추가한다.
- NATS URL은 `nats://<서버 IP>:4222` 형식의 실제 예시를 제시한다.
- Agent마다 `AgentId`와 `CameraIndex`가 일치해야 한다는 배치표를 추가한다.
- 실카메라 설치 후 시험 캡처, 저장 파일 생성, Master 결과 수신까지 확인하는 종단 간 검증 절차를 추가한다.
- `hardware.json`과 `agent.json` 수정 전 백업, JSON 문법 오류 확인, 수정 후 재시작 절차를 추가한다.
- USB 카메라와 USB 시리얼 장치의 절전 해제로 인한 연결 끊김 방지 항목을 추가한다.
- PLC·셔터·서보를 실제로 구동하기 전 비상정지와 작업 구역 안전 확인 경고를 눈에 띄게 배치한다.
- 장애 분석을 위해 Master와 Agent 로그의 위치 및 수집 방법을 추가한다.
- 운영 배포가 프레임워크 종속인지 자체 포함인지 한 방식으로 결정하고, 그 방식에 맞는 설치 절차만 제시한다.

## 이미지 자리 검토
- [그림 2] 부분적 적절 — NATS 기동 확인 위치는 유용하지만 단순히 컨테이너 실행 화면만 보여 주지 말고 컨테이너 이름, 상태, 포트 매핑이 식별되도록 캡처해야 한다.
- [그림 3] 적절 — 설정 파일 생성 위치 확인에 도움이 된다. 주소 표시줄과 `hardware.json`, `data.db` 파일명이 보이되 사용자 계정명 등 개인정보는 가리는 것이 좋다.
- [그림 4] 부분적 적절 — 카메라와 COM 포트 확인을 한 화면에 담는 것은 유용하지만 장치 관리자만으로 `CameraIndex`를 확정할 수 없다는 설명이 필요하다. 가능하면 Agent의 시험 영상 또는 탐색 결과 화면을 함께 제시한다.
- [그림 5] 적절 — Agent 정상 기동 판단에 유용하다. 실제 로그 문구, Agent ID, NATS 주소, CameraIndex가 식별되도록 하고 민감한 네트워크 정보는 마스킹한다.
- [그림 6] 적절 — Master가 Agent를 인식한 결과를 보여 주는 핵심 이미지다. 녹색 점만 강조하지 말고 Agent ID와 온라인 상태 또는 마지막 하트비트 영역을 표시해야 한다.
