# 04-설정-파일-레퍼런스 — 검토 종합 (Round 1)

## 판정

- Codex: 수정 필요도 상. 필드 구조·편집 절차·라우팅 설명 보강 요구는 대체로 타당하나 일부 런타임 의미를 잘못 추정했다.
- Claude: 수정 필요도 중. NATS/Serial, AgentManager 파일, PLC 실제 키 누락 지적에 수렴했다.
- agy: 수정 필요도 중. PLC·흑체·Agent 세부 필드 누락을 정확히 짚었으나 `BlackBody.Enabled` 설명은 현재 코드와 맞지 않는다.
- kimi: 수정 필요도 중. AgentManager 경로, Alias 폴백, 누락 필드 지적은 코드와 일치한다.
- 종합: 네 리뷰는 “설정 레퍼런스의 실제 필드명·중첩 구조·적용 조건을 보강해야 한다”는 결론에 수렴한다. 다만 `DataRetentionDays=0`, `BlackBody.Enabled`, Manager 상태 파일 생성 시점에서는 리뷰 또는 매뉴얼과 현재 코드가 충돌한다.

## 합의·다수 수정 (코드 확인됨)

- [4.1 파일 위치] `manager-settings/state.json`처럼 보이는 표기는 실제 구성을 오해시킴 -> `{InstallRoot}\Manager\manager-settings.json`과 `manager-state.json`을 분리하고, InstallRoot는 첫 실행 인수로 바뀔 수 있음을 명시한다. 설정 파일은 없으면 메모리 기본값만 사용하고 자동 생성하지 않는다. (Codex, Claude, kimi)
- [4.1 레시피] `recipe/*.json` 생성 시점이 불명확함 -> `FileRecipeRepository` 초기화 때 `recipe`와 `recipe bak` 폴더가 생성되고, 개별 `{Recipe.Id}.json`은 레시피 저장 시 생성된다고 명시한다. 레시피는 `data.db`가 아니라 JSON 파일에 저장된다. (Codex)
- [4.1 공통 편집 절차] 적용 시점과 JSON 오류 대응이 없음 -> Master·Agent·AgentManager 모두 시작 시 설정을 읽으므로 해당 프로세스를 종료한 뒤 백업·편집하고 재시작하도록 안내한다. 기본 `System.Text.Json` 설정상 주석과 후행 쉼표는 허용되지 않는다. (Codex, Claude, kimi)
- [4.1 data.db] 직접 편집 위험이 설명되지 않음 -> LiteDB가 촬영·챔버·알람 이력, 대시보드 레이아웃, 카메라 설정·장치 정보를 관리하므로 직접 편집하지 말라고 명시한다. (Claude, kimi)
- [4.2 Nats/Serial] 최상위 필드만 있고 세부 레퍼런스가 부족함 -> `Nats.Url`과 셔터 전용 `Serial.PortName/BaudRate/DataBits/Parity/StopBits`를 실제 기본값과 함께 별도 표로 유지한다. (Codex, Claude, agy, kimi)
- [4.2 CameraPairings] 배열 요소와 매핑 기준이 누락됨 -> 실제 키 `CameraUsbParentId`, `PortName`, `ClSerialNumber`, `DisplayName`을 표로 제시한다. (Codex, kimi)
- [4.2 DataRetentionDays] 삭제 범위와 주기가 모호함 -> 앱 시작 1분 후, 이후 24시간마다 `ImageCache` 아래 `.jpg`와 촬영 이력만 정리한다고 명시한다. Agent의 `ImageStorage`, 챔버 이력, 알람 이력은 현재 정리 대상이 아니다. (Codex, kimi)
- [4.3 PLC 필드] `Temp*`, `Eq*`, `Admin*`, `BitJog*±` 축약으로 JSON 키를 찾기 어려움 -> 실제 속성명을 개별 행으로 제시하고 주소를 1:1 대응시킨다. (Codex, Claude, kimi)
- [4.3 PLC 주요 항목] 운영 관련 필드가 빠짐 -> 최소한 `BitErrorReset`, `BitBuzzerOff`, `PulseHoldMs`, `CoordinateMoveDelayMs`, 홈·에러·상태·IO base 및 관리자 경계값의 실제 키를 보강하거나 `PlcSettings` 전체 목록을 별도 부록으로 연결한다. (Claude, agy, kimi)
- [4.3 스케일] `value×10 → short` 설명이 불충분함 -> `Math.Round(value×scale)` 후 `short`로 변환하며 별도 범위 검사나 포화 처리가 없음을 명시한다. 온·습도는 ×10, 흑체는 ×100이다. (Codex)
- [4.4 BlackBody.Units] COM4/COM5 요약만으로 구조를 알 수 없음 -> `ConnectionType=Serial`이면 COM 및 115200 8N1, `Ip`이면 IP 주소와 포트를 사용한다고 실제 요소 필드를 구분한다. `ReadTimeoutMs`, `InterMessageDelayMs`, `SimulatedRampCelsiusPerSecond`도 포함한다. (Codex, agy, kimi)
- [4.4 RecipeEngine] 허용오차와 타임아웃의 실제 사용이 불명확함 -> `TemperatureTolerance`는 챔버와 흑체의 절대 온도차 판정에 공통 사용되고, `CaptureResultTimeoutSeconds`와 `RampStepIntervalSeconds`도 시작 시 읽힌다고 설명한다. 값 검증은 코드에 없다. (Codex, agy)
- [4.5 agent.json] `LogPath`, `CameraModel`이 누락됨 -> `LogPath`가 비면 exe 기준 `logs`, `CameraModel` 지정 시 exe 기준 `CameraModels\{CameraModel}.json`을 읽으며 실패하면 카메라 기본 해상도를 사용한다고 명시한다. (agy, kimi)
- [4.5 AgentId] 기본값·CLI 우선순위가 불명확함 -> 파일 값이 비었을 때 머신명을 사용하며 CLI 첫 번째 인수가 있으면 최종적으로 이를 덮어쓴다고 설명한다. (kimi)
- [4.5 StoragePath] 경로 형식 설명이 부족함 -> 절대 경로는 그대로, 상대 경로는 Agent exe 폴더 기준으로 해석됨을 명시한다. 저장 서비스가 디렉터리를 생성하지만 생성·쓰기 실패 시 캡처 실패가 될 수 있다. (Codex)
- [4.6 라우팅] Alias 경로를 단정적으로 설명함 -> `CameraAlias`가 있으면 `ICameraDeviceRepository.GetByAliasAsync` 결과의 `AgentId`를 우선 사용하고, Alias 미설정·조회 실패·AgentId 공백이면 `Agent_{CameraIndex}`로 폴백한다고 수정한다. (Codex, kimi)
- [4.6 CameraIndex] 0/1 예시와 코드 주석의 1~64가 충돌함 -> 기본값과 런타임은 0을 허용하며 범위 검증이 없다는 현재 사실을 명시하고, 설치 현장의 인덱스 규칙을 별도로 확정한다. (kimi)
- [4.7 AgentManager] 설정·상태 파일이 위치 표에만 머묾 -> `ManagerSettings`와 `ManagerState/CameraEntry`의 실제 필드를 별도 절에서 설명한다. (Claude, kimi)

## AI 지적이 부정확 (코드검증)

- `DataRetentionDays=0`이면 정리하지 않는다는 주장과 매뉴얼 문구는 현재 구현과 다르다. `BackgroundDataCleanupService`에는 0 예외 처리가 없어 cutoff가 현재 시각이 되며, 기존 촬영 이력과 `ImageCache` JPEG 대부분이 삭제 대상이 된다. (Codex, kimi)
- `BlackBody.Enabled=true`일 때만 SR-800N 직접 제어를 사용한다는 설명은 현재 코드와 맞지 않는다. `CreateBlackBodyController`는 `SimulationMode`가 아니면 `Enabled`와 무관하게 `SrBlackBodyController`를 만들며, 이 컨트롤러는 온도 설정 시 SR 링크와 PLC 양쪽에 쓴다. `Enabled`는 현재 `PlcStatusService`에 흑체 컨트롤러를 전달할지 결정하는 데만 사용된다. (Codex, agy의 제안문)
- `manager-state.json`이 승인 시에만 생성된다는 주장은 부정확하다. AgentManager가 새 카메라를 발견하여 `Upsert`하는 시점에도 즉시 저장된다. (kimi)
- `CameraIndex`가 반드시 1~64라는 근거는 모델 주석뿐이며 코드 검증이나 런타임 제한은 없다. 기본값은 0이고 `Agent_0` 라우팅도 동작한다. (kimi가 인용한 범위 주장)

## 보류 (설비 안전/도메인 확인 필요)

- `ServoSpeedPercent(D2560)`, `BitEmergencyStop(M2000)`, `BitJogYPlus/Minus(P725/P726)`, `ServoPointYBase(D3012)`는 코드상 placeholder다. 실제 PLC 명세와 배선 확인 전 운영값으로 확정하지 않는다.
- `UseHexBitIndex=true`는 XBC-DN64H(XGB) 전제의 코드 기본값이다. 비트 오독 시 임의 반전하지 말고 실제 PLC 주소 체계를 확인해야 한다.
- `PulseHoldMs`, `CoordinateMoveDelayMs`, SR-800N 타임아웃·메시지 간격의 적정값과 허용 범위는 실제 설비 응답 및 제조사 규격 확인이 필요하다.
- PLC 주소 변경, 챔버·서보·비상 관련 조작 절차와 백업·복구 기준은 설비 담당자의 안전 절차 확인 없이 문서에 새로 만들지 않는다.
- `TemperatureTolerance`의 허용 범위와 0·음수 처리 정책은 코드에 검증이 없으므로 운전 도메인 기준을 확정한 뒤 문서화해야 한다.
