# 06-시리얼-셔터-프로토콜 — codex 검토 (Round 1)

## 종합 평가
- 수정 필요도: 중
- 한 줄 요약: 명령 바이트는 명확하지만, 캐시 상태의 한계와 모델 변경 절차에 필요한 안전 경고 및 검증 단계가 부족하다.

## 수정 필요 항목
1. [명령 바이트 표기] 문제: 설명 문장이 코드 블록 안에 있어 명령 데이터로 오인할 수 있고, “3번째 바이트”는 시작 위치가 불명확하다. -> 제안: 명령만 코드 블록에 두고, “왼쪽부터 세 번째 바이트(오프셋 2)”라고 별도로 설명한다.
2. [상태 조회] 문제: 소프트웨어 캐시가 실제 셔터의 물리적 상태를 보장하지 않는다는 점이 드러나지 않는다. 통신 실패, 전원 재시작 또는 수동 조작 시 실제 상태와 다를 수 있다. -> 제안: 캐시 값은 “마지막으로 요청한 상태”일 뿐이며, 유지보수 시 셔터를 육안으로 확인해야 한다는 경고를 추가한다.
3. [다른 셔터 모델] 문제: 버퍼 수정만으로 다른 모델을 지원할 수 있는 것처럼 안내한다. 모델에 따라 통신 조건, 명령 길이 및 응답 방식도 달라질 수 있다. -> 제안: 제조사 프로토콜을 먼저 확인하고 담당 개발자가 구현 변경, 동작 검증 및 재배포를 수행하도록 안내한다.
4. [파일 경로] 문제: `Protocols/SerialShutterController.cs`는 저장소 기준 경로인지 배포 PC에서 찾을 경로인지 불명확하다. -> 제안: “소스 코드 파일”임을 명시하고 실제 저장소 상대 경로와 일치하는지 확인한다.

## 누락/추가 제안
- 상태 조회를 지원하지 않으므로 설치 후 열기·닫기 명령을 각각 전송하고 실제 셔터 동작을 육안으로 확인하는 검증 절차를 추가한다.
- 시리얼 포트 및 통신 조건 설정 방법을 다루는 장의 링크를 추가한다. 이 장에는 프로토콜 바이트만 유지해 중복을 피한다.
- `cameraIndex`는 로그·호출 대상 식별에만 사용되고 전송 데이터에는 포함되지 않는다는 설명을 코드 블록 밖에 유지한다.

## 이미지 자리 검토
- 이미지 자리 없음 — 7바이트 명령 설명에는 이미지가 필수적이지 않다. 다만 설치 대상자가 포트와 셔터 연결을 구분해야 한다면 별도의 배선·포트 대응 그림이 유용하다.

## (선택) 수정 제안 전문

# 6. 시리얼 셔터 프로토콜

셔터는 7바이트 raw binary 명령으로 제어한다. ASCII 문자열 명령이 아니므로 아래 값을 바이트 배열로 전송해야 한다.

```text
열기: 0x04 0x00 0x01 0x00 0x00 0x00 0x00
닫기: 0x04 0x00 0x00 0x00 0x00 0x00 0x00
```

두 명령은 왼쪽부터 세 번째 바이트(오프셋 2)만 다르다.

- 열기: `0x01`
- 닫기: `0x00`
- `cameraIndex`는 셔터 식별에만 사용하며 전송 버퍼에는 포함하지 않는다.

## 상태 확인 시 주의사항

하드웨어 상태 조회는 지원하지 않는다. 프로그램이 반환하는 상태는 마지막으로 요청한 명령을 기준으로 저장한 소프트웨어 캐시이다.

> 주의: 캐시 상태는 셔터의 실제 물리적 상태를 보장하지 않는다. 통신 실패나 장치 전원 재시작 후에는 표시 상태와 실제 상태가 다를 수 있으므로 유지보수 시 셔터 동작을 육안으로 확인한다.

설치 또는 통신 설정 변경 후에는 열기와 닫기 명령을 각각 실행하여 실제 동작을 확인한다.

## 다른 셔터 모델 적용

다른 셔터 모델을 적용할 때는 먼저 제조사의 통신 프로토콜과 시리얼 통신 조건을 확인한다. 담당 개발자가 소스 코드의 `SerialShutterController` 명령 버퍼와 필요한 통신 처리를 변경하고, 실제 장치에서 열기·닫기 동작을 검증한 후 재배포한다.
