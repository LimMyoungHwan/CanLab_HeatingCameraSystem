## 합의·다수 수정 (코드 확인됨)

- [3.1 사전 요구사항] 빌드 PC와 운영 PC의 .NET 요구사항이 불명확함 -> 빌드 PC는 .NET 8 SDK, Master PC는 Windows Desktop Runtime 8, Agent PC는 .NET Runtime 8로 구분한다. 현재 게시 명령은 자체 포함 배포가 아니다. (근거 AI: Codex, agy, Kimi)
- [3.1·3.3 NATS 준비] Docker 사용 전제와 실행 위치가 불명확함 -> 저장소 루트의 PowerShell에서 실행한다고 밝히고 `docker version`, `docker compose version` 확인을 추가한다. 명령 블록도 PowerShell 기준임을 표시한다. (근거 AI: Codex, Claude, Kimi)
- [3.2 방화벽] 통신 방향과 대상이 모호함 -> NATS 호스트 4222 인바운드, Master·Agent 4222 아웃바운드, Master 2004 아웃바운드로 구분하고 Agent가 PLC와 직접 통신하지 않음을 명시한다. (근거 AI: Codex, Claude, Kimi)
- [3.2·3.3 NATS 검증] `127.0.0.1` 검사만으로 원격 접속을 검증함 -> NATS 호스트에서는 localhost, Master·Agent에서는 실제 NATS 주소로 4222 연결을 검사하고 `hardware.json`·`agent.json`에 같은 주소를 설정한다. (근거 AI: Codex)
- [3.3 NATS 서버] 컨테이너 실행 여부만 확인함 -> `docker compose ps`, 로그, 4222 포트와 `restart: unless-stopped`를 함께 확인한다. 현재 Compose는 8222를 매핑하지만 모니터링 활성화 옵션은 없다고 명시한다. (근거 AI: Codex, Kimi)
- [3.4 Master 설치] 게시 대상과 실행 위치가 불명확함 -> 저장소 루트에서 `HeatingCameraSystem.Master\HeatingCameraSystem.Master.csproj`를 명시해 게시하고 실제 실행 파일명 `HeatingCameraSystem.Master.exe`를 사용한다. (근거 AI: Codex)
- [3.4 Master 설정] `hardware.json` 수정 항목과 적용 순서가 모호함 -> 최초 실행, 파일 생성 확인, Master 종료, `Plc.IpAddress`, `Plc.Port`, `Nats.Url`, `Serial.PortName` 및 현장 PLC 주소 확인, 재실행 순서로 작성한다. (근거 AI: Codex, Claude, agy, Kimi)
- [3.5 Agent 설치] 실행 파일명과 초기 설정 절차가 불명확함 -> `HeatingCameraSystem.Agent.exe`로 통일하고 최초 실행 후 `AgentId`, `CameraIndex`, `NatsUrl`, `StoragePath`, `SimulationMode`를 수정한 뒤 재실행하도록 한다. (근거 AI: Codex, agy, Kimi)
- [3.5 Agent CLI] 인수 형식과 설정 우선순위가 불명확함 -> `<AgentId> <NatsUrl> [CameraIndex] [StoragePath] [SimulationMode] [LogPath]` 순서를 제시하고, 기존 `agent.json`을 먼저 읽은 뒤 제공된 인수만 덮어쓴다고 설명한다. `SimulationMode`는 `true`/`false`이다. (근거 AI: Codex, agy, Kimi)
- [3.5 다중 Agent] 동일 설정으로 여러 인스턴스를 실행하면 충돌 가능함 -> 인스턴스별 `AgentId`와 `StoragePath`를 분리하고 `CameraIndex`를 실제 카메라와 맞춘다. (근거 AI: Codex)
- [3.6 카메라 확인] 장치 관리자 순서로 OpenCV `CameraIndex`를 확정함 -> 장치 관리자에서는 장치 존재만 확인하고 Agent 초기화 또는 시험 캡처 성공으로 인덱스를 검증한다. 장치 재연결 후에는 다시 확인한다. (근거 AI: Codex, Kimi)
- [3.6 시리얼 셔터] COM 포트와 통신 방식 설명이 부족함 -> COM 번호는 Master의 `hardware.json`에 있는 `Serial.PortName`에 반영하고, 기본 `COM3`, 9600 8N1은 현장값과 대조한다. 셔터는 ASCII가 아닌 7바이트 raw binary이므로 Master 기능으로 시험한다. (근거 AI: Codex, Claude, Kimi)
- [3.7 런타임 검증] `dotnet --info 8.x`를 명령처럼 제시함 -> `dotnet --list-runtimes`에서 Master는 `Microsoft.WindowsDesktop.App 8.x`, Agent는 `Microsoft.NETCore.App 8.x`를 확인한다. (근거 AI: Codex, Kimi)
- [3.7 Agent 검증] 실제 출력과 다른 로그 문구를 제시함 -> `Connected to NATS (...)`와 `Camera idx=N ready (SIM|REAL)`로 수정하고 실제 캡처·저장·결과 수신까지 확인한다. (근거 AI: Codex, agy, Kimi)
- [3.7 Master 인식] “초록 점”만으로 정상 여부를 판정함 -> 대시보드에서 Agent ID, `CAM-NN`, 카메라 상태를 확인하고 마지막 하트비트 후 15초가 지나면 오프라인으로 판정됨을 명시한다. (근거 AI: Codex, agy, Kimi)
- [3.7 PLC 상태] 갱신 기준이 모호함 -> 실PLC 설치에서는 대시보드 상태가 1초 폴링에 따라 갱신되는지 확인하되 정상 범위는 현장 기준을 따르도록 한다. (근거 AI: Kimi)
- [전체 운영 준비] 저장 공간·로그·재시작 이후 운용 조건이 빠짐 -> Agent의 `StoragePath`·`LogPath`와 Master 데이터 경로의 권한·용량을 점검하고, 자동 시작은 별도 구축이 필요한지 명시한다. (근거 AI: Codex, Claude, Kimi)
- [전체 상호참조] 설치 실패 시 후속 안내가 없음 -> NATS·PLC·카메라 장애는 기존 트러블슈팅 장으로 연결한다. (근거 AI: Claude, Kimi)

## AI 지적이 부정확 (코드검증)

- [전체 그림 번호] `[그림 1]`이 누락됐다는 지적은 부정확하다. `[그림 1]`은 2장에 있으며 3장의 `[그림 2]` 시작은 매뉴얼 연속 번호 체계와 일치한다. (근거 AI: Claude, agy)
- [3.4 설정 키] `NatsUrl`, `PlcSettings.IpAddress`, `SerialSettings.PortName`은 `hardware.json`의 실제 경로가 아니다. 올바른 경로는 `Nats.Url`, `Plc.IpAddress`, `Serial.PortName`이다. (근거 AI: Claude, agy)
- [3.5 CLI 우선순위] CLI 인수를 사용하면 `agent.json`을 무시한다는 주장은 틀리다. 파일이 있으면 먼저 읽고 전달된 인수만 해당 필드에 덮어쓴다. (근거 AI: agy)
- [3.6 COM 설정] COM 포트를 Agent의 `ShutterPort`에 설정한다는 제안은 현재 구조와 다르다. 시리얼 셔터는 Master가 제어하며 `hardware.json`의 `Serial.PortName`을 사용한다. (근거 AI: Claude)
- [3.3 NATS 모니터링] 8222를 개방하면 곧바로 모니터링 화면을 사용할 수 있다는 전제는 틀리다. 현재 Compose에는 NATS HTTP 모니터링 활성화 인수가 없다. (근거 AI: Codex, agy, Kimi)
- [자동 시작·비-Docker NATS] Windows 서비스 등록, 시작프로그램 등록, `nats-server.exe` 설치는 현재 저장소가 제공하는 기능이 아니다. 지원 절차로 단정하지 말고 별도 운영 정책으로 구분해야 한다. (근거 AI: Claude, agy, Kimi)
- [8222 접속 주체] 모니터링 접속 주체를 Master PC 웹 브라우저로 고정할 코드상 근거가 없다. 승인된 관리 PC 또는 관리망으로 표현해야 한다. (근거 AI: agy)
- [OpenCV 선행조건] Visual C++ 재배포 패키지의 별도 설치가 반드시 필요하다는 근거는 현재 프로젝트 설정에서 확인되지 않는다. 실제 게시물·대상 PC 검증 없이 필수 요구사항으로 추가하지 않는다. (근거 AI: Kimi)

## 보류 (설비 안전/도메인 확인 필요)

- [3.4 PLC 주소] `BitEmergencyStop`, `ServoSpeedPercent`, Y축 JOG 비트, `ServoPointYBase`는 현장 명세 확인이 필요한 플레이스홀더다. 실제 PLC 도면·주소표와 대조하기 전 값을 확정하지 않는다. (근거 AI: Codex)
- [3.7 실장비 시험] PLC 쓰기, 서보 이동, 셔터 개폐의 승인 절차·안전 조건은 코드로 결정할 수 없다. 비상정지와 작업 구역 조건을 포함한 현장 안전 절차 확인 후 문서화한다. (근거 AI: Codex, Kimi)
- [3.7 온습도] 정상 범위는 코드에 정의된 설치 기준이 아니므로 설비 담당자가 제공해야 한다. (근거 AI: Kimi)
- [3.2 보안] 8222 공개 범위와 관리자 접근 정책은 현장 네트워크·보안 담당자 확인이 필요하다. 사용하지 않는 경우 개방하지 않는 원칙만 제시한다. (근거 AI: Codex)
- [운영 정책] 자동 시작 방식, 서비스 계정, 이미지 보존·정리 주기, USB 절전 설정, 비-Docker NATS 운영 여부는 현장 운영 정책 확인 후 추가한다. (근거 AI: Codex, Claude, agy, Kimi)
